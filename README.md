# niryo_teleop — Ned2 master + teleop controller (Chunks 2–4)

Teleoperate one Niryo **Ned2** with another Ned2.

> **Going to hardware?** Start with [`docs/PHYSICAL_SETUP.md`](docs/PHYSICAL_SETUP.md):
> robot prep, driver bridge, config, first teleoperation session, safety rules.

- `/master/joint_states`: `sensor_msgs/msg/JointState` (measured master state, Chunk 3)
- `/actor/joint_cmd`: `trajectory_msgs/msg/JointTrajectory`, single-point streaming
  command later forwarded to the actor's `FollowJointTrajectory` controller.

## Chunk 3 — master joint-state publisher

Architecture (no duplicated Niryo functionality):

```text
Physical Ned2 master
  -> ned-ros2-driver (official bridge, rosbridge :9090) publishes
     sensor_msgs/JointState on /joint_states (or /<ns>/joint_states)
  -> master_joint_state_publisher (validated relay, this repo)
  -> /master/joint_states (sensor_msgs/JointState, measured state only)
```

The node subscribes the driver's topic, validates (sizes, exact Ned2 joint
names, finite positions), rate-caps via `publish_rate_hz`, and republishes
preserving `header.stamp` and joint order. `velocity`/`effort` are forwarded
only when present with matching length, else published empty — never
fabricated. No input beyond `stale_timeout_sec` → throttled warnings, nothing
stale published; recovers automatically. Robot IP/port/namespace live in the
driver's own config, not here — only `input_topic` points at it
(`src/niryo_teleop/config/master_params.yaml`).

Ned2 interface: 6 joints, `radians`, `[joint_1..joint_6]` base→tip, in order.

Hardware run (actor driver still out of scope):

```bash
# terminal 1: official driver (separate workspace ~/projects/niryo_driver_ws, needs robot on LAN)
source /opt/ros/jazzy/setup.bash
source ~/projects/niryo_driver_ws/.venv/bin/activate  # driver venv, needs autobahn==23.6.2 (see docs/PHYSICAL_SETUP.md)
source ~/projects/niryo_driver_ws/install/setup.bash
ros2 launch niryo_ned_ros2_driver driver.launch.py drivers_list_file:=$HOME/projects/niryo_driver_ws/src/ned-ros2-driver/niryo_ned_ros2_driver/config/master_driver.yaml
# master_driver.yaml: rosbridge_port 9090, robot_namespaces ["master_raw"], robot_ips ["169.254.200.200"]
# terminal 2: this project
source /opt/ros/jazzy/setup.bash
source install/setup.bash
ros2 launch niryo_teleop master.launch.py  # adjust input_topic if namespaced
```

Inspect:

```bash
ros2 topic list | grep -E 'joint_states|master'
ros2 topic info /master/joint_states   # expect sensor_msgs/msg/JointState
ros2 topic echo --once /master/joint_states
ros2 topic hz --window 30 /master/joint_states
```

Manual-move check: put the master in learning/compliant mode, move it by hand,
`position[]` must track. Verified here with `scripts/mock_ned2_driver.py`
(sine sweep): two `--field position` samples 1 s apart differed on all joints;
`hz` showed ~31 Hz against a 50 Hz mock (equal-rate phase beating of the
rate cap — set `publish_rate_hz` ≥ driver rate for a lossless relay).

Remaining hardware-dependent config: driver robot IP/hostname + namespace
(`input_topic` must match), `publish_rate_hz` vs measured driver rate
(`ros2 topic hz /joint_states`), learning-mode enable for hand-guiding.

## Chunk 4 — teleoperation controller

```text
/master/joint_states (sensor_msgs/JointState)
  -> subscriber stores latest (no processing in callback)
  -> fixed-rate loop @ control_rate_hz (default 50 Hz)
     validate_master_state -> map_master_to_actor -> apply_joint_limits
     -> build_actor_command -> publish_actor_command
  -> /actor/joint_cmd (trajectory_msgs/JointTrajectory, single point)
```

Mapping by default is identity (`q_cmd = q_master`, scale 1.0 / offset 0.0);
per-joint `joint_scale` (negative = inversion), `joint_offsets`, and
`joint_limits_min/max` (Ned2 defaults) are params, length-checked at startup
(misconfiguration aborts instead of commanding wrong joints). Extension point
for filtering/velocity-limiting/remapping sits between map and limit stages.
Output: `joint_names` + one point with `positions`, empty `velocities`
(controller interpolates), `time_from_start` (default 0.2 s), stamped at
publish time. Stale input (no message within `stale_timeout_sec` 1.0 s, or
stamp older than `maximum_state_age_sec` 0.5 s) → publish nothing, throttled
warnings, auto-recovery. Node name `teleoperation_controller`
(`src/niryo_teleop/config/teleop_params.yaml`); legacy executable
`teleop_controller_node` runs the same entry point.

Verify without actor (actor scope stops at the topic):

```bash
# programmatic input while controller runs:
ros2 topic pub --rate 10 /master/joint_states sensor_msgs/msg/JointState \
  "{header: {stamp: {sec: 0, nanosec: 0}, frame_id: ''},
    name: ['joint_1','joint_2','joint_3','joint_4','joint_5','joint_6'],
    position: [0.5,-0.5,1.0,0.0,0.25,-0.25], velocity: [], effort: []}"
ros2 topic echo --once --field points /actor/joint_cmd  # expect same positions
# full chain with Chunk 3 (terminal each: mock driver, teleop.launch.py):
ros2 topic hz --window 40 /master/joint_states
ros2 topic hz --window 40 /actor/joint_cmd
```

Measured here (mock sine @50 Hz → master relay → controller): master ~32 Hz
(known rate-cap beating, Chunk 3), actor exactly 50.000 Hz (σ 0.0001 s),
transport delay ~0.0 ms. Direct-pub identity check passed exactly
([0.5,-0.5,1.0,0.0,0.25,-0.25] in → out); stale-stop verified (echo times out
>1 s after input stops, `dropping invalid master state (stale stamp…)` logged).
